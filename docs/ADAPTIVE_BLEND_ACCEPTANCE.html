三、缺陷清单(4 项,均经运行时或 diff 实证)

高 D2 · overlap_frames 是死旋钮 —— 提交信息与文档 §4 失实

位置 nodes.py #48 build_hardcut_plan(…)(L330)与 #56 同调用(L689);geometry 硬编码 "overlap_frames": 0(L343/L702)

  • 提交 44142ca 信息声称 "#56 and #48 gained an overlap_frames widget … wired into both build calls",但该 commit 对 nodes.py 的 diff 只有 4 个 hunk(2 个 widget + 2 个函数签名),没有任何一处把参数传入 build_hardcut_plan。运行时源码复查确认:两处调用点至今未传参。
  • 后果:UI 上可设 overlap_frames=17,plan 里的 temporal_overlap_frames 永远是 0,行为与硬切无异。文档 §4 首行参数声明因此失实。
  • 影响面:仅全局手动旋钮。自适应路径不受影响 —— calm_overlap_frames 走 plan.hardcut 通道,已实测接通(A2/A3/B6)。
  • 修复:两处调用各加一行 overlap_frames=max(0, int(overlap_frames)),并将 geometry 中的硬编码 0 一并替换。

中 C1 · I3 只对"计划切点"生效,最终边界可产生 17 帧碎段(实测反例)

位置 h3_upscale.py find_calm_boundaries 候选过滤(L141-144)

  • min_sep 过滤的比较对象是其他计划切点(for other in planned),不是已输出的最终边界;可靠切点的 hunt 边界(±deviation 内)更不做任何间距检查。
  • 实测:计划切点 [204, 238](相距 34),204 的 hunt 边界漂移到 221(+17,可靠),238 平缓搜索选中 238 → 最终边界 [221, 238],间距 17 帧,产生 17 帧碎窗 —— 正是 §3.4 I3 声称"不产生"的东西。
  • 触发条件较窄(需 seam_tolerance ≥ 17 且计划切点仅相距 34),但 I3 被文档列为可测试不变量。
  • 修复:候选过滤改为对"已输出的最终边界 + 其余计划切点"检查。

中 C2 · 两条缝可选中同一平缓帧 → 切点静默丢失 → 窗合并/OOM(实测反例)

位置 同上;与文档 §3.2 伪码不一致

  • 文档 §3.2 写的是 far_enough_from(other_boundaries, MIN_SEP)(对最终边界),代码实现的是对 planned 切点 —— 文档与代码不一致。
  • 实测:计划切点 [85, 153](相距 68,均为合法窗长),中点 119(距两者各 34,通过两边的过滤)恰为全局最平缓帧 → 两条缝都选 119,输出 boundaries=[119, 119]。
  • explicit_segments 的 sorted(set(…)) 去重后只剩一刀 → 3 窗变 2 窗、负载翻倍 —— 正是 I7/§5("不得丢弃;丢弃会导致两窗合并 → OOM")明确要防的场景,但该防线只覆盖 hunt 路径,平缓搜索路径绕过了它。
  • 修复:同 C1 —— 过滤对象改为已输出边界即可同时堵住这两个洞(文档版算法本来就是对的)。

低 C3 · locked_overlap_tokens 旋钮失效(单位错位,恒全锁)

位置 h3_upscale.py L817-819 传参处

  • 上游 _append_video_guarded_overlap(…, locked_overlap_tokens) 期望 token 数;执行器传入的是帧值(seg_overlap/计划里的帧数)。由于重叠区 token 数 ≤ 帧数,min(帧值, token数) 恒等于 token 数 = 全锁。
  • 实测:计划取 0 / 5 / 17 / 999,输出全部与"全锁"逐比特相同 —— 该参数任何取值都不改变行为。
  • 行为本身与 §3.3 的描述("回读部分完全保留旧结果,不做混合")一致,输出没有错;但 §4 把它列为可调参数("重叠区中完全保留旧结果的 token 数")构成失实。
  • 修复:传参处把帧换算成 token(seg_overlap // FRAME_GRID * 5)或从 §4 删除该行。
